# Mint 埋点项目接手说明

## 这件事要达成什么

楚涵负责整理 Mint 的埋点需求，与科技、产品对齐后交付开发和 GrowingIO 配置。要让重要流程可计算到达、转化、失败和业务结果，并能追溯事件对应页面、控件或后台业务事实。前端负责真实展示与操作等事实；后台、数仓已有且可靠的业务状态优先核查真实数据来源，不为了凑埋点在前端重复统计。

涉及注册、登录、资格申请与贷款服务开户、借款与放款、还款及相关权益、设置安全与隐私、首页服务与返现。当前需求按已有 UI 和已知后台场景整理。正常还款之外的异常流程及尚无 UI 的场景，范围仍待产品确认；不能宣称已覆盖全部情况。

## 文件怎么用

| 文件 | 用途 | 当前状态 |
| --- | --- | --- |
| `baseline/md/Mint_V2.0.0_埋点需求_单文档评审版.md` | 会议审核的详细需求原稿，可按 `RG-E001` 等编号查触发、位置、属性、验收 | 原件归档，内容多，尚未按会议要求精简 |
| `baseline/excel/Mint_埋点开发清单_统计方式_V7.xlsx` | 事件及统计方式的 V7 清单，与 MD 对照 | 原件归档；V8 事件命名方案未启用 |
| `baseline/manifest.json` | 原件大小、校验值 | 用于验证原件未被改写 |
| `docs/2026-10-14_会议修改清单.md` | 原始笔记提出的七项要求及字段分类方法 | 会议建议，细节仍需核实 |
| `docs/2026-10-14_会议待办与决策.md` | 视频核对摘要新增事项、楚涵待办、科技产品数据团队待确认 | 当前工作清单，以用户提供摘要为依据 |
| `docs/CODEX_接续任务.md` | 下一轮产物及工作顺序 | 接手执行说明 |

新产物放在 `requirements/`。原件中的需求编号要保持可追溯；修订时写明保留、合并或暂缓的去向。对于 MD 和 V7 不同之处，逐条记录证据与确认状态。页面、按钮、API 发起、后台受理、业务结果和结果页展示是不同事实。V7 中同一个事件标识符可在不同页面复用，依据属性区分；若科技确定改为独立事件，应先形成命名决定，再同步开发需求与 GIO 配置。

## 下一轮实际工作

1. 从 MD 与 V7 提取全量字段、枚举、适用需求、来源和必传条件，标记示例值、冲突及无来源字段；形成字段字典、枚举表、待确认问题。
2. 对照 GrowingIO 官方埋点规范核查事件、属性、代码上报及平台配置要求，记录规范版本和实际接入差异；平台能力或原始数据导出未经核实不可写成已支持。
3. 与产品和科技逐项确认白名单客群、手机锁安装/激活授权/取消后的行为、当前 UI 与具体 Figma 节点、异常还款范围、字段来源和触发点。
4. 整理科技可直接实施的短版需求：公共字段集中解释，逐事件保留固定值、特有字段、触发与不触发、采集端、去重和验收；从正文移出“保留删除理由”等评审文字。
5. 形成与最终开发需求一致的 GIO 配置清单及责任分工；对账数据需求单独明确两侧数据、记录范围、提供方式和负责人，再与数据团队对接。

楚涵负责需求整理与问题汇总；科技确认代码、后台数据及平台接入；产品确认业务口径和 UI；数据团队确认对账数据来源、权限和交付。会议未确定具体截止日期和上述未决问题的答案。

## 开始工作时的核查

- 先读 README、AGENTS、两份会议文档和接续任务，再看原件目录及相关章节。
- 核对 `main` 最新状态及 manifest；保留他人修改，基线不改。
- 每次交付报告改了哪些需求编号、还有哪些问题及谁负责、字段覆盖情况、仓库提交链接。
